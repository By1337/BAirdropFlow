# Редактор аирдропов

Статический интерфейс на JS-модулях и SVG. Зависимостей npm нет; браузер получает
список аирдропов, JSON-схемы компонентов и конфиги через настоящий BWebTunnel.
Редактор поддерживает добавление, удаление, переименование и перемещение нод,
связи `create` / `remove` / `destroy` / `call`, параметры компонентов, undo/redo и масштаб.
Связь создаётся перетаскиванием от выхода к нужному входу: линия видна во время
перетаскивания. Конец стрелки можно перенести на другой вход; отпускание на пустом
месте отвязывает связь. Esc отменяет жест, Ctrl+Z возвращает изменение.
ПКМ по фону создаёт ноду на месте курсора, по ноде открывает быстрые действия,
по связи — переподключение и удаление. У компонентов, кроме `__init__` и
`__destroy__`, есть отдельный вход `remove`; вызываемые события представлены
своими входами, например `update` у голограммы.
Название в инспекторе меняет только подпись в редакторе, технический ID остаётся
прежним. Цвет и размер ноды хранятся в метаданных редактора. Каждую ноду можно
растянуть за нижний правый угол: ширина 260–760, высота до 780 пикселей. Все поля
компонента видны внутри ноды, содержимое прокручивается; правый инспектор остаётся
для подробного редактирования. Note — свободная заметка с текстом.

Команды редактируются как YAML прямо внутри обработчика каждой ноды, например
`- bc: Привет всем` или `- '[setblock] 10 10 10 air'`. Многострочный текст
и градиенты сохраняются. Редактор проверяет YAML через серверный парсер;
`create`, `remove`, `call`, `destroy` принимаются только как связи на схеме.
`__destroy__` принимает связь `destroy`.

Отдельных командных нод нет. Старые визуальные командные блоки удаляются из
метаданных при загрузке; команды из подключённых блоков уже находятся в
обработчиках нод.

Заметки хранятся в `$web_meta.webNodes`, подписи компонентов — в
`$web_meta.nodes.<id>.title`. В исполняемом `nodes` нет web-типов.

Обработчики команд показываются как YAML. Сложные вложенные условия,
`weights` и неизвестные поля нод сохраняются; полный JSON ноды доступен в
дополнительном разделе инспектора для ручного редактирования особых случаев.

## Сборка и установка

Сначала соберите изменённый BWebTunnel: новый client и backend используют
протокол 2 с POST. Старые клиенты продолжают работать через GET; POST для
клиента с протоколом 1 возвращает HTTP 501.

```bash
mvn -f ../BWebTunnel/pom.xml install
mvn package
npm --prefix web run build
```

Плагину нужна Java 21+. Сборке BWT backend и запуску тестового прокси нужна
Java 25+, поскольку существующий backend собирается под Java 25.
`client:1.0` включён в плагин и перемещён в `dev.by1337.baf.libs.web`;
backend подключён только для тестов.

Установите новый JAR плагина и обновлённый backend BWT. Скопируйте содержимое
`web/dist/bairdropflow` в каталог статики nginx на том же домене, что `/api/`.
Пример маршрутов: [nginx.conf.example](nginx.conf.example). API и статика
используют один origin; при другом домене настройте проксирование API через nginx.
Если у BWT уже есть настройки dashboard, сохраните их и добавьте маршрут статики
редактора. Обновление backend на VDS автоматически не выполняется.

В `plugins/BAirdropFlow/config.yml`:

```yaml
web:
  enabled: true
  url: 'wss://tunnel.example.com/api/ws'
  static: bairdropflow
  secret: '' # можно указать существующий секрет группы BWT
  description: 'Аирдропы: survival-1'
```

После перезапуска `/baf web` выдаёт ссылку `https://host/<token>/bairdropflow/`.
Право `baf.web.admin` по умолчанию есть у op. Токен даёт доступ к редактированию
конфигов этой ноды. Список загружается заранее из `workflow/**/*.yml` и `.yaml`;
ошибочные конфиги тоже видны в каталоге. `/baf start <файл>` запускает загруженный
сценарий, `/baf` запускает `default.yml`.

## Сохранение

`GET /api/<token>/airdrops` — каталог, `/schemas` — схемы, `/airdrop?key=...` —
полный конфиг, метаданные и SHA-256 revision.
`POST /api/<token>/commands/parse` принимает `{ "yaml": "- bc: Привет" }`,
возвращает список команд и отклоняет команды связей.

`POST /api/<token>/airdrop`, `Content-Type: application/json`:

```json
{
  "key": "default.yml",
  "revision": "revision из GET",
  "nodes": {
    "__init__": { "type": "__init__", "on_init": [] },
    "__destroy__": { "type": "__destroy__", "on_destroy": [] }
  },
  "metadata": {
    "version": 3,
    "nodes": { "__init__": { "x": 40, "y": 60 } },
    "viewport": { "x": 0, "y": 0, "zoom": 1 }
  }
}
```

Можно дополнительно передать `settings` с `id`, `world`, `args`, `generator`,
`spawner`. Остальные поля корневого YAML сохраняются. `nodes` полностью заменяется,
`$web_meta` хранится одной JSON-строкой. Перед записью конфиг проверяет
`Workflow.CODEC`; исходные байты копируются в
`backups/workflow/<время-uuid>/<файл>`, затем файл заменяется атомарно.
Форматирование YAML и комментарии могут поменяться при пересериализации;
в бэкапе остаётся точный оригинал.

При чужом изменении файла возвращается `{ "ok": false, "code": "conflict", ... }`.
Нужно перезагрузить конфиг. Ошибки валидации возвращаются в JSON с `ok: false`.
Лимиты: POST 512 KiB, метаданные 64 KiB, ответ 1 MiB, максимум 512 нод.
Успешное сохранение обновляет загруженный сценарий: новые запуски берут новый
конфиг, уже запущенные спавнеры и аирдропы продолжают работать со своим экземпляром.

## Добавление компонентов

Регистрируйте декодер и схему вместе:

```java
AirdropComponent.REGISTRY.register("custom:node", Config.DECODER,
    NodeSchema.of("Моя нода", "Описание")
        .integer("timer", "Время", 20, 1, false)
        .events("on_create", "on_remove")
        .inputs("create", "remove"));
```

Схема идёт из реестра на фронтенд и определяет библиотеку компонентов и поля
инспектора. Серверный декодер остаётся источником правил валидации.
`dh:hologram` доступен, когда зарегистрирована интеграция DecentHolograms.

## Локальная проверка без Paper

```bash
npm --prefix web test
npm --prefix web run build
mvn test
mvn test-compile dependency:build-classpath -Dmdep.outputFile=target/editor-classpath.txt
python3 web/dev-server.py
```

Последняя команда поднимает настоящий backend из test-зависимости на порту 18083,
подключает настоящий WS-client, отдаёт `web/dist` через `GetStaticContentHandler`
и печатает `EDITOR_URL`. Пример конфигурации создаётся в отдельной временной папке;
файлы установленного плагина не используются. Для своих путей и порта:

```bash
python3 web/dev-server.py /tmp/my-airdrops web/dist 18083
```

Maven-тесты проверяют POST через WS, большие UTF-8 тела, сохранение метаданных,
бэкапы, revision-конфликты, отказ для неверных конфигов и обхода путей, а также
совместимость маршрутов GET. Тесты Node проверяют вложенные связи, undo/redo и
изменения во время сохранения. Отладочный `RunTest` запускает сервер превью и
ждёт Ctrl+C; для обычного прогона используйте `mvn -Dtest='*,!RunTest' test`.
